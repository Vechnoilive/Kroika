# Архитектура Kroika

Версия контрактов: **1.0.0** · Этап: **3/15** · Стиль: модульный монолит.

## Главное решение

Веб-приложение, работа с AI, хранение и математический движок будут отдельными модулями одного репозитория. Между ними передаются только документы, прошедшие версионированные контракты. Pattern Engine не импортирует FastAPI, UI или SDK Qwen/Gemini и не принимает изображения.

```mermaid
flowchart LR
    UI["Web UI"] --> API["Backend API"]
    API --> STORE["Проекты и изображения"]
    API --> AI["AIProvider"]
    AI --> API
    API --> ENGINE["PatternEngine"]
    ENGINE --> API
```

AI возвращает предложение о видимых признаках. Пользователь подтверждает фасон, ткань и настройки. Только после этого backend формирует `PatternEngineRequest` и передаёт его независимому движку. Эта граница не позволяет ответу модели напрямую стать выкройкой.

## Контракты предметной области

Все схемы используют JSON Schema 2020-12, запрещают неизвестные поля и имеют версию `1.0.0`. Каноническая единица длины — mm.

| Сущность | Назначение | Ключевая защита |
| --- | --- | --- |
| `BodyMeasurements` | Профиль ручных мерок и происхождение каждого значения | Статус `ready` требует все входы текущей методики; cm допускаются только как сохранённый исходный ввод |
| `GarmentSpec` | Подтверждённые человеком параметры фасона | Предложение AI и подтверждённый фасон имеют разные схемы и статусы |
| `FitSettings` | Прибавки на свободу, модельные прибавки и припуски | Три набора не смешиваются; доли переда/спинки проверяются отдельно |
| `FabricProperties` | Структура, стабильность, растяжимость и назначение ткани | Подтверждённая ткань не может сохранять значения `unknown` |
| `FormulaRecord` | Формула, единицы, источник, область и доказательства проверки | Все 41 записи этапа 2 проходят схему; production требует полного набора проверок |
| `PatternProject` | Сохраняемый агрегат проекта с ревизией и историей | Версии метода и результата не меняются молча; связи проверяются по ID и hash |
| `ValidationReport` | Машиночитаемые проверки и понятные сообщения | Блокирующая ошибка исключает производственный экспорт |

Вспомогательные схемы определяют AI-запрос/ответ, запрос/ответ Pattern Engine и каноническую геометрию `PatternData`. Геометрическая схема уже различает линии, кубические Безье и дуги, однако математическая реализация этих типов относится к этапу 6.

## Поток данных

```mermaid
flowchart TD
    A["Ручные мерки cm или mm"] --> B["Нормализация в mm"]
    C["Изображения"] --> D["AIStyleAnalysis"]
    D --> E["Подтверждение человеком"]
    B --> F["PatternEngineRequest"]
    E --> F
    F --> G["input_hash"]
    G --> H["PatternEngine"]
    H --> I["PatternData + ValidationReport"]
```

`input_hash` вычисляется из значений, способных изменить геометрию или область применимости. Имена, ID, время подтверждения и происхождение мерки в hash не входят. Изменение любой мерки, прибавки, конструктивного параметра, свойства ткани или версии методики меняет hash. JSON канонизируется с сортировкой ключей; `NaN` и бесконечности запрещены.

Повторный запрос с тем же hash в будущем должен вернуть тот же сохранённый результат либо геометрически эквивалентный результат той же версии движка. Идемпотентное хранение будет реализовано на этапе 4.

## Границы модулей

| Модуль | Получает | Возвращает | Чего внутри нет |
| --- | --- | --- | --- |
| Web UI | Представления API | Подтверждённые пользовательские действия | Формул построения и API-ключей |
| Backend API | JSON/файлы от UI | OpenAPI-ответы на русском | Собственной геометрии |
| AI adapter | `AIAnalysisRequest` с 1–4 ссылками на подготовленные изображения | `AIStyleAnalysis` | Мерок тела, прибавок и координат лекал |
| Pattern Engine | Подтверждённый `PatternEngineRequest` | `PatternEngineResult` | Изображений, SDK провайдеров, HTTP и базы данных |
| Persistence | Версионированные проекты и служебные записи | Копии конкретной ревизии | Неявных миграций при чтении |

Python-интерфейсы находятся в [ports.py](../src/kroika_contracts/ports.py). Они используют `Protocol`, поэтому mock, Qwen и Gemini смогут иметь один интерфейс без общей SDK-зависимости. Текущие реализации провайдеров и движка появятся на следующих этапах.

## Структура будущего монорепозитория

Этап 4 добавит `frontend`, `backend` и отдельный пакет `pattern-engine`. Папка `src/kroika_contracts` останется общей контрактной библиотекой. Backend будет единственным модулем, который связывает хранилище, адаптер AI и движок.

```text
frontend/                 React + TypeScript + Vite
backend/                  FastAPI, application services, SQLite adapters
pattern-engine/           чистый Python, геометрия и методики
src/kroika_contracts/     схемы, hash, смысловые проверки, порты, миграции
schemas/                  канонические JSON Schema и OpenAPI
examples/                 проверяемые примеры документов
tests/                    контрактные и последующие тесты
```

## Ошибки для пользователя

JSON Schema проверяет форму документа, затем semantic validation проверяет отношения полей: сумму долей прибавки, соответствие исходных cm нормализованным mm, отношение дуг к полным обхватам, область ткани и поддержанную комбинацию фасона. Ошибки имеют стабильный `code`, JSON Pointer и сообщение по-русски. Backend сможет подсветить конкретное поле без показа трассировки или секретов.

Текущая методика `experimental`, поэтому контракт не может разрешить производственный экспорт. Диагностический результат и производственный файл имеют отдельные флаги. Архитектурный gate этапа 3 не меняет незакрытый экспертный gate методики этапа 2.

## API

[openapi.v1.yaml](../schemas/openapi.v1.yaml) фиксирует девять операций: анализ изображений, создание/чтение/сохранение проектов, генерацию, отчёт, SVG, PDF и JSON-экспорт. `PUT` использует номер ревизии через `If-Match`, чтобы одна вкладка не затёрла изменения другой. Обработчики, авторизация локального режима и хранилище реализуются на этапе 4.
