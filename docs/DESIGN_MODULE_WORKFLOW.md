# Реестр модулей и независимый ввод мерок

Первый шаг расширения моделирования объединяет правила существующих модулей и защищает передачу подтверждённых деталей от редактора до PDF. Новая геометрия драпировок, каскадных воланов и асимметрии будет добавляться отдельно.

## Единый источник поддержки

`src/kroika_contracts/design_modules.json` содержит идентификатор, группу, допустимые сочетания изделия/типа/варианта/расположения/конструкции и диапазоны размеров каждого реализованного модуля. Все значения размеров — в миллиметрах. Интерфейс показывает сантиметры.

Python-адаптер `design_modules.py` и TypeScript-адаптер `frontend/src/designModules.ts` читают один файл. Семантическая проверка и редактор используют одинаковые правила; хеширование и компиляторы берут из него группы модулей. JSON включён в Python-пакет через `setuptools.package-data`.

У элемента отдельно заданы обязательные и необязательные размеры. Остальные поля должны быть пустыми: компилятор не принимает числа, которые не применяет к геометрии. Для известной конструкции с неверными размерами редактор показывает «Проверьте размеры», а не «Нужен модуль».

Чтобы добавить модуль, необходимо реализовать геометрию, зарегистрировать правила и размеры, подключить доказательство `design_coverage`, проверить соединения и экспорт. Запись в реестре сама по себе не создаёт лекало: существующая проверка покрытия отклонит модуль без геометрического результата.

## Мерки до завершения фасона

Шаг 4 доступен любому сохранённому проекту, включая черновик с неподдержанной драпировкой. Автосохранение мерок сохраняет открытый шаг и выбранные детали. Подтверждение готового фасона, мерок и настроек по-прежнему продвигает обычный последовательный путь.

Ввод и сохранение мерок не подтверждают фасон. Неподдержанная включённая деталь остаётся в проекте и блокирует построение до реализации или явного исключения пользователем.

## Защита генерации от устаревших входов

Клиент передаёт ревизию проекта в `If-Match` при `POST /api/v1/patterns/generate`. Сервер проверяет ревизию, подтверждение сохранённых входов и геометрический хеш проекта перед обращением к кешу/движку. Проверка повторяется в транзакции непосредственно перед привязкой результата, включая кешированный результат. Проверка подтверждения обязательна: ещё не реализованная драпировка может не менять геометрический хеш, но должна остановить запрос старого подтверждённого фасона.

Изменение ревизии возвращает `409 PROJECT_REVISION_CONFLICT`; несовпадающий геометрический запрос — `409 GENERATION_INPUTS_STALE`. Даже клиент без заголовка не может привязать старый базовый запрос к проекту с сохранённым воланом. Изменение проекта во время вычисления также не публикует устаревшую генерацию.

Клиент строит запрос из сохранённого фасона без скрытого изменения `coverage_schema_version`. Старые проекты сохраняют прежний хеш-контракт до явной проверки и сохранения конструктивного плана; новый редактор записывает актуальную версию покрытия.

## Проверяемый сценарий волана

Для существующего кругового волана по низу:

| Поле | Значение |
| --- | --- |
| Тип | `flounce` |
| Вариант | `circular` |
| Расположение | `hem` |
| Конструкция | `separate_piece` |
| Количество | `1` |
| Глубина | 8 см = 80 мм; допустимо 3–40 см |
| Ширина, длина, расстояние | Пустые |
| Модуль | `circular_hem_flounce_v1` |

Регрессионный сценарий сохраняет и открывает проект с этим воланом и юбочной подкладкой, строит 10 деталей, повторно получает ту же генерацию из кеша и проверяет наличие названий всех деталей в A4 PDF вместе с квадратом 50×50 мм. Это проверяет путь существующего кругового волана; каскад от талии требует другой геометрии.

`tests/test_design_module_workflow.py` проверяет сервер, конкурирующее изменение и PDF; `frontend/src/DesignModuleWorkflow.test.tsx` проверяет размеры, сохранение, повторное открытие, хеш и ввод мерок при неполном фасоне. Оба набора подключены к текущей команде `scripts/verify_stage27.py`.
